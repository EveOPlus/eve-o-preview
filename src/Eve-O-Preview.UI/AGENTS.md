# Portable workspace UI

Read [the source instructions](../AGENTS.md) and [application/configuration guide](../docs/ai/application-and-configuration.md).

- This project targets portable `net10.0`. Keep Windows APIs, `System.Drawing`, profile filesystem operations, native handles and authentication secrets out of the UI. Platform operations cross `IWorkspaceBackend`.
- Light and Dark receive new features. Legacy is locked to its current feature set for legacy use only: do not add new features, pages or controls. Continue bug fixes, compatibility work and updates to existing features through shared commands/settings, preserving the compact layout and original WinForms control positions. Users are expected to migrate to a modern theme; keep the brief feature-availability notice when selecting Legacy.
- Title editing must keep its preview visible and use `IWorkspacePreviewRenderer` when available. On Windows this paints the actual live overlay control. Never multiply the configured font size or replace user colors with theme colors; distinguish fitted preview scaling from the configured values.
- A global theme is independent of the active profile. `ProfileAccentColor` is optional profile identity, not the game's preview-highlight color. Keep arbitrary accent colors out of body text to preserve contrast.
- New and older/unversioned global settings start in Dark. After migration, an explicit theme choice (including Legacy) must survive restart and profile switches. Let `ApplicationPreferences` own this policy; do not reset the theme whenever an older gameplay profile loads.
- New editable settings need portable catalog metadata, host validation/mapping, persistence and runtime application. Preserve in-progress drafts on background refresh; confirm before discarding drafts on a profile switch.
- New modules use `WorkspaceModule` and belong in modern themes only; do not expose them through Legacy navigation or extension routes. Planned ESI/DPS pages must not imply authentication or telemetry already exists.
- Linux is an internal architecture target, not a user-facing promise. Keep future Linux support out of UI copy and the public user guide; retain portability plans in developer documentation.
- Use FC (Fenris Creations) for the company name in new UI and status messages. Do not reintroduce the former CCP branding; preserve actual service URLs, API identifiers and historical attributions.
- Keep UI copy concise: clear labels, necessary setup instructions and actionable status/errors. Put detailed explanations in README guides instead of permanent help paragraphs beside every control.
- Only when working on Chinese translations (`zh-Hans` or `zh-Hant`), read [the Chinese translation guide](Localization/CHINESE.md) and follow its contextual wording examples alongside the shared catalog rules.
- When adding, renaming or changing features/settings, update settings search at the same time: labels, common aliases and section destinations. Include terms people use (for example DPS/reps and log/logs), match localized labels, and verify each result opens the relevant section. Module sections belong in `WorkspaceModule.SearchTargets`; individual settings belong in `SettingCatalog`.
- Reuse `WorkspacePickers.FontFamily` for standard font dropdowns, `Search` for searchable item lists, and `Color` for compact popup colour selection. Font dropdowns have a visible scrollbar. Colour controls edit the caller's draft; preserve each page's existing Apply/Save contract. Popup palettes and RGB controls are shared, including Title & Highlight. Localize display templates, never stored enum values or raw character/item/font names.
- Render actual controls using [the visual smoke harness](../tests/Eve-O-Preview.UI.Smoke/) and test the Windows backend/lifetime adapter separately. Headless renders do not verify native focus, game injection or real monitor DPI.

## Future workspace modules

- **Current state:** Characters/ESI remains hidden. The host registers Augments (stable ID `Dps`) through [CombatLogView](CombatLogView.cs), with alpha/DPS overview, thumbnail appearance/simulation and automatic/manual source settings. It is modern-only. `WorkspaceModules.ReservedIds` retains both IDs; dormant planned renderers remain unavailable. Use "thumbnail augments" in new user-facing controls; these graphics belong to thumbnails, not EVE client windows.
- **Register a ready feature:** implement a `WorkspaceModule` with a stable ID, title, description and `CreateView` factory. Supply it through `WorkspaceView` from [WorkspaceForm](../Eve-O-Preview/View/Implementation/WorkspaceForm.cs). Trace host service registration through `Program.CreateApplicationContainerBuilder`. Registered modules gain modern navigation/search entries. `IWorkspaceModuleDrafts` retains unapplied fields and participates in discard guards; `IWorkspaceLiveModule` updates without rebuilding controls on background notifications. Disposable module views are disposed when leaving the page. Legacy must not expose registered modules.
- **Complete the backend first:** ESI authentication and token storage/refresh remain unimplemented. [Combat logs](../docs/ai/combat-logs.md) use host ingestion/storage and the portable `IWorkspaceCombatLogs` capability. Public identity and portrait services remain separate; cached IDs do not provide authentication. Keep native handles and filesystem access out of page state and reuse the global settings/profile storage policy.
- **Preserve identities and scope:** distinguish full client window titles from EVE character IDs; decide which settings belong to a profile or to the application. Follow [the integration boundaries](../docs/ai/application-and-configuration.md#future-platform-and-integration-boundary) and [DPS/ESI requirements](../docs/ai/ui-review.md#future-dps-and-esi-extension-requirements). Do not replace the existing Clients page or add one top-level tab for every future option.
- **Before exposing navigation:** verify real success, empty/loading/error states, draft persistence, disposal, profile/theme switches and keyboard access in Light and Dark. Add focused host integration checks for persistence/authentication/data processing. Keep unfinished modules unregistered and their links hidden.
